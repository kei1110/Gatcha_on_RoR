# DEVELOPMENT_WORKFLOW — スライス実行体制（折衷案 v2）

1 スライス（= 1 ブランチ = 1 PR・squash マージ）の標準実行体制。0b-5 で v1 を、1-1 で v2 効率化 5 項目を実測検証し、生き残った形を成文化したもの。**「誰が何をやるか」の規約であり、「何を作るか」は docs/ROADMAP.md・docs/SPEC.md が正**。

## 基本形（役割分担）

| 工程 | 担当 | 根拠（実測） |
|------|------|--------------|
| brainstorm・設計・多視点レビュー triage | 主エージェント | 判断の文脈を持つ者が設計する |
| 設計段階の多視点レビュー | 独立サブエージェント並列（視点ごと・互いの結論を見せない） | 0b-5/1-1 とも設計の実バグを実装前に検出（例: 1-1 の SPEC §5.3 深夜帯単窓） |
| 実装計画（**コード全文を計画に書く**） | 主エージェント | 計画への投資が下流の知力要求を転写レベルに下げる — v2 全項目の前提 |
| 実装 | サブエージェント（モデルは下記②） | フレッシュな文脈・3 か条で品質担保 |
| スペック準拠レビュー | **主エージェントが git diff 直接突合** | 約 30 万トークン/スライス削減（0b-5 実測）・検出力低下なし |
| 品質レビュー（敵対的） | 独立サブエージェント（下記③④） | 著者バイアス対策の本丸。0b-4 で 4 件・1-1 で 6 件の実指摘 |
| マージ前最終 | tenant-isolation-reviewer（models/migrations 変更時）・labor-law-compliance-reviewer（calculator/compliance 変更時） | CLAUDE.md のエージェント規約 |

## 効率化 5 項目（1-1 で実証済み）

1. **処方箋完全 かつ 差分 10 行以下の修正は主エージェントが直接適用** — 検証コマンド実行必須。サブエージェントへの差し戻しは「調査・判断が残る修正」のみ（1-1 で 4 回適用・問題ゼロ）
2. **計画が全コードを持つ転写型タスクは haiku** — プロンプトに「転写タスク・改変禁止・失敗したら直さず BLOCKED 報告」を明記。逸脱が出たら即 sonnet へ戻す（1-1 で 3/3 完走・逸脱ゼロ・52〜119 秒/タスク）。判断が混じるタスク（schema 確認・既存コード統合・UI 検証）は sonnet
3. **レビュアーに実挙動検証の義務** — プロンプト定型句:「主張する前に実挙動で検証せよ — spec 実行・`RAILS_ENV=test bin/rails runner`・gem ソース。机上推論だけの High 以上指摘は禁止。検証不能な主張は確信度を明示せよ」。実測では最高価値の指摘は全て実験由来・偽陽性は全て机上推論由来（0b-5/1-1 で一貫）。レビュアーの実験が新しい罠を踏んだら GOTCHAS の収穫として記録する（1-1 で 3 件）
4. **品質レビューのバッチ化** — 結合の強い隣接タスクは 1 レビュー（1-1: サービス 3 タスク・UI 2 タスクをバッチ・検出力低下なし）。スキーマ・認可など心臓部タスクは単独
5. **Codex は診断専用** — 転写タスクで 25 分停滞 vs sonnet 4 分の実測（0b-5）により定常実装から除外。Rails バグ級の怪現象の独立診断に限定

## サブエージェントへのディスパッチ規約

- **計画ファイルを読ませない** — タスク全文（コード込み）をプロンプトに転載する
- **3 か条を毎回注入**: ①ステップ完了ごとに即コミット ②不要だった編集は revert してから報告 ③検証コマンド（rspec・`rubocop --force-exclusion`・app/ に触れたら brakeman）を明記し実行結果を報告させる
- **docs/RAILS_GOTCHAS.md を注入**（該当する罠の要点をプロンプトへ転記。フックはサブエージェントをすり抜けるため指示で補う）
- 報告形式を固定: DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED + 検証実出力 + コミット SHA。**BLOCKED に同条件再試行はさせない**（文脈追加・モデル昇格・分割・計画修正のいずれかを変える）

## 罠の還流（このループが本体制の利息）

実装者・レビュアーが踏んだ/仕留めた罠は**同じブランチで** docs/RAILS_GOTCHAS.md へ追記する。1-1 の例: `delete_all` の nullify 化（レビュアーの実験が実踏）・`travel_to` 外 `follow_redirect!` のセッション切れ（実装者が計画の配置ミスを検出）・devise FailureApp の 302 固定（レビュアーの gem ソース確認）。

## 改訂

本書は実測で更新する。項目の追加・削除は「スライス 1 周の実測 → triage → 本書改訂」の順で行い、根拠の実測値を残すこと。
