# ユーザーストーリー動線マップ（SPEC §1.4）+ 到達性 DoD 昇格 — 設計

> 状態: 承認済（2026-06-24 brainstorming）。本書は実装計画（writing-plans）の入力。
> 出典: Phase 3 完了時の `/spec-check`（5観点）。技術4観点（§3/§4/§5/§6・§7/§13）は Critical/High 乖離ゼロだったが、**第5観点（ユーザーストーリー網羅）が動線断絶を検出**（完了済み機能が URL 直打ち専用）→ PR #19/#20 で是正。本設計はその観点を**再現可能な仕組み**に昇華する。

## 1. 目的（Why）

縦切りスライス（モデル＋サービス＋spec で「動く」を定義）は機能を確実に届ける一方、**機能間を繋ぐ横断的な到達性（ユーザーが端から端まで辿れるか）がどのスライスの完了条件にも属さず落ちる**——これが Phase 2〜3 で起きた動線断絶の構造的原因だった。

処方箋は「ユーザーストーリーを別管理する」ことではない（§1.1/§1.2 に機能はアクター別に列挙済・§12 に UI 記述あり）。本当に欠けていたのは **(a) アクター起点の到達性を一覧で検証できる基準表** と **(b) それを各スライスの完了条件（DoD）に組み込む規約** の 2 点。本設計はこの 2 点を、SSOT 規律と drift 防止に整合する最小形で導入する。

## 2. 決定事項（brainstorming で確定）

| 論点 | 決定 | 理由 |
|---|---|---|
| 成果物の粒度 | **ハイブリッド薄型**: 1 行 = アクターの 1 目的 + 起点(route+nav)併記 | 到達性（起点列が空＝断絶）も将来フロー（目的/結果）も 1 枚で検証可能 |
| 配置 | **SPEC §1.4 新設**（§1.2 主要機能・管理者向けの直後） | アクター別機能列挙（§1.1/§1.2）の自然な接続点。**別ファイルにすると §12 UI と drift** するため SPEC 同居 |
| カバー範囲 | **既存（Phase 0a〜3）を網羅 + 状態列**。Phase 4-5 は行を先作りせず | ROADMAP/§8/§9 と内容重複・drift を避ける。全体像は ROADMAP が持つ |
| 成長 | **DoD で成長**: 新機能スライスが自分の行を §1.4 に追加 | 表が自然に育ち、かつ ROADMAP の二重管理にならない |
| 非ゴール | Jira 風の独立 user-story バックログ／Phase 4-5 スタブ行／Gherkin 形式 | YAGNI・SSOT 最小主義（CLAUDE.md「フェーズ番号をベタ書きしない」と同方針の drift 嫌い） |

### 3.3 §1.4 の不変条件（メンテ規約）

- 本表は**動線到達性の SSOT**。`状態` が `✅` の行は「起点 route が実在し、nav 入口（または明示された画面内導線）からクリック到達でき、結果（副作用）まで一周する」ことを意味する。
- `⚠️` は「起点はあるが表示・継ぎ目に欠けがある」既知状態。空の `起点 route` または欠落 `nav 入口` は **未検出の断絶の疑い**＝レビューで指摘対象。
- Phase 4+ の新機能は実装スライスで行を追加する（本設計時点では先作りしない）。
